01

Core Research Framework

Most data-science learners can run PCA().fit(X) or loss.backward() well before they can say what those calls compute. The math is taught as symbol manipulation, and the ML is taught as API calls. Little connects the two. MathMatrix AI is built on one claim: the gap is about representation, not difficulty. Students rarely see one idea expressed at the same time as an equation, a picture, running code, and a model behavior.

Where students get stuck

F9Feedback latencyA wrong derivation gets noticed days later, or neverStep-level feedback doesn't scale with instructors alone

Theoretical grounding

Multiple linked representations

Ainsworth: changing one view (a matrix entry) immediately updates the others (equation, plot, code). Targets F1, F3, F6.

Cognitive load theory

Sweller: worked examples and faded scaffolding shape the step-by-step derivation engine.

Self-explanation effect

Chi et al.: the tutor asks students to explain a step before it explains it.

Productive failure

Kapur: modules open with an attempt before instruction, such as tuning a learning rate by hand.

Bloom's 2-sigma problem

LLM tutors approximate one-on-one tutoring only if their math is verified, so every AI feature has a verification layer.

Research questions

  1. 1

    Conceptual transfer. Do linked interactive representations with AI narration produce larger concept-inventory gains than static text with the same exercises?

  2. 2

    Tutor design. Does a Socratic, hint-first tutor beat an answer-first tutor on delayed post-tests, at the cost of more time on task?

  3. 3

    Verification. Does CAS-backed checking keep student-facing math errors under 1% of claims, and does a visible "verified" label change trust and learning?

  4. 4

    Bridging. Do math-to-ML labs (e.g., PCA from the SVD) improve students' ability to debug real ML code?

Study design

  • Design: student-level A/B randomization within cohorts, with features toggled by flag; crossover where modules are independent.
  • Instruments: per-module pre/post concept inventories (8–12 misconception-based items), a delayed post-test at 3–4 weeks, a transfer task (debug a broken ML notebook), and process data such as hint depth, simulator parameters explored, and tutor turns.
  • Analysis: mixed-effects models with student and module random effects; normalized gain $g = \frac{\text{post}-\text{pre}}{100-\text{pre}}$.
  • Ethics: IRB approval before identifiable data; opt-in dialogue logging; PII removed before any LLM call; a visible "AI may be wrong" notice with a way to report errors.

    ML bridge. The same idea inside a real model, then a misconception quiz.

03

Interactive AI Feature Specifications

Four rules apply to every AI feature.

Ground, then generate

The model always gets the module's knowledge pack and the live state of the page.

Verify the math

Symbolic claims go through SymPy; numbers are computed in the browser.

Hint before answer

Socratic by default; full solutions unlock after attempts.

One notation

Column vectors, numerator-layout Jacobians, $\boldsymbol\theta$ for parameters, everywhere.

A

"Muddiest Point" Clarifier

Targets F2 · F4 · F5 · F8 · F9

At the end of each section the student writes what confused them most. The tutor matches it to a known misconception, asks one probing question, explains using the page's visual, then checks understanding.

Interface
  • Slide-over panel from a "Still muddy?" button or a text selection
  • Streaming replies with live math rendering
  • "Show me" buttons that set the page's visual to a specific state
  • A verified badge on CAS-checked equations
  • Screen-reader math and full keyboard support
Prompt strategy
  • Layered system prompt: teaching contract → notation → knowledge pack → misconception taxonomy, all cached; page state goes in the user turn
  • Diagnose → probe → explain → check
  • Tools: check_equivalence (SymPy) and set_visual_state
  • Won't solve graded items; hands off to the instructor after 3 unresolved loops
System prompt sketch
You are the MathMatrix AI tutor for Module {module_id}: {module_title}.

Teaching contract:
- Diagnose before you explain. Match the student's confusion to an entry in
  <misconceptions>. If unsure which one, ask ONE short probing question first.
- Prefer the student's own reasoning: ask them to predict or explain a step
  before you reveal it.
- Tie every explanation to the interactive visual on the page. When a specific
  configuration would make the point, offer it with the set_visual_state tool.
- Before stating any algebraic identity or derivative, verify it with
  check_equivalence. If verification fails, say so and fix it.
- Write math in LaTeX. Keep replies under ~150 words unless asked for more.
- End with one short check-for-understanding question.

Gradient Descent Flight Simulator + AI Coach

Targets F7 · F4

Students fly an optimizer over a loss surface, tuning learning rate, momentum, and conditioning, and see each choice tied back to theory.

Interface
  • Contour plots: rotated quadratic, Rosenbrock, Himmelblau, saddle, noisy logistic loss
  • Controls for $\eta$ (log scale), momentum, $\kappa$, optimizer, and start point
  • Theory overlay marking $2/\lambda_{\max}$ and $\eta^\star$ on the slider

Prompt strategy
  • The browser computes the facts (eigenvalues, $\eta\lambda_{\max}$, loss ratios, oscillation counts); the model only interprets them
  • Structured JSON output: regime, evidence, theory link, suggested experiment, question
  • One few-shot example per regime

05

Prototype Module: Gradient Descent

Module 9 is the first vertical slice. It exercises every layer: LaTeX lesson content, Python that runs in the browser, an interactive visual, and two AI endpoints.

The mathematics

Near a minimum every smooth loss looks like a quadratic, so that is the model problem:

$$f(\mathbf{x})=\tfrac12\,\mathbf{x}^\top A\,\mathbf{x}-\mathbf{b}^\top\mathbf{x},\qquad A=A^\top\succ0,\qquad \nabla f(\mathbf{x})=A\mathbf{x}-\mathbf{b},\qquad \mathbf{x}^\star=A^{-1}\mathbf{b}.$$

With error $\mathbf{e}_k=\mathbf{x}_k-\mathbf{x}^\star$, one step gives $\mathbf{e}_{k+1}=(I-\eta A)\,\mathbf{e}_k$. In the eigenbasis each component scales by $(1-\eta\lambda_i)$, so gradient descent converges exactly when

$$0<\eta<\frac{2}{\lambda_{\max}},\qquad \eta^\star=\frac{2}{\lambda_{\min}+\lambda_{\max}},\qquad \lVert\mathbf{e}_{k+1}\rVert\le\frac{\kappa-1}{\kappa+1}\lVert\mathbf{e}_k\rVert,\quad \kappa=\frac{\lambda_{\max}}{\lambda_{\min}}.$$

The takeaway for students

The steepest direction sets the learning-rate ceiling, and the flattest direction sets the speed. When $\kappa$ is large, the step that keeps the steep direction stable is slow in the flat direction, and the path zig-zags. This links Module 5 (eigenvalues) to Module 9 (optimization) to practice (feature scaling).

Try it: the simulator runs this exact quadratic. Push $\eta$ past $0.2$ and watch it diverge.

Open the simulator →

Python (runs in Pyodide and in the code lab)

import numpy as np

def make_quadratic(lam_min=1.0, lam_max=10.0, theta=np.pi / 6):
    R = np.array([[np.cos(theta), -np.sin(theta)], [np.sin(theta), np.cos(theta)]])
    A = R @ np.diag([lam_min, lam_max]) @ R.T
    b = np.array([1.0, 1.0])
    return A, b, (lambda x: A @ x - b)

def gradient_descent(grad, x0, lr, momentum=0.0, steps=100, tol=1e-8):
    x, v = np.asarray(x0, float), np.zeros(2)
    path = [x.copy()]
    for _ in range(steps):
        g = grad(x)
        if np.linalg.norm(g) < tol:
            break
        v = momentum * v - lr * g          # heavy-ball momentum
        x = x + v
        path.append(x.copy())
    return np.array(path)

A, b, grad = make_quadratic()
x_star = np.linalg.solve(A, b)
for lr in [0.05, 0.182, 0.19, 0.21]:
    p = gradient_descent(grad, np.array([-2.0, 2.0]), lr)
    print(f"lr={lr:.3f}: final error={np.linalg.norm(p[-1] - x_star):.2e}")
# verified output (κ = 10, η_max = 0.200, η* = 0.182)
lr=0.050: final error=1.24e-02   # too timid: slow in the flat direction
lr=0.182: final error=6.58e-09   # optimal fixed step
lr=0.190: final error=7.16e-05   # near the ceiling: oscillates, still converges
lr=0.210: final error=3.71e+04   # 5% past 2/λ_max: diverges

SymPy verification tool

Every algebraic claim the tutor makes can be checked with this tool. parse_expr uses eval internally, so it must run in a sandbox: a subprocess with limits, or the Pyodide worker.

# api/app/verify.py
import json, sympy as sp
from sympy.parsing.sympy_parser import (
    parse_expr, standard_transformations, implicit_multiplication_application)

TRANSFORMS = standard_transformations + (implicit_multiplication_application,)
SYMPY_NS: dict = {}
exec("from sympy import *", SYMPY_NS)

def check_equivalence(lhs: str, rhs: str, variables: str) -> str:
    syms = {v.strip(): sp.Symbol(v.strip(), real=True) for v in variables.split(",") if v.strip()}
    try:
        a = parse_expr(lhs, local_dict=dict(syms), global_dict=SYMPY_NS, transformations=TRANSFORMS)
        b = parse_expr(rhs, local_dict=dict(syms), global_dict=SYMPY_NS, transformations=TRANSFORMS)
    except Exception as e:
        return json.dumps({"status": "parse_error", "detail": str(e)})
    diff = sp.simplify(a - b)
    return json.dumps({"status": "equivalent" if diff == 0 else "not_equivalent",
                       "difference": str(diff)})

Streaming tutor endpoint

The stable prompt layers come first and are cached, so repeat questions on a module reuse them. Page state goes in the user turn. Server-side fallbacks retry automatically if the model declines a request.

# api/app/tutor.py
@app.post("/api/clarify")
def clarify(req: ClarifyRequest):
    user_turn = (f"<page section='{req.section}'>\n"
                 f"<visual_state>{json.dumps(req.visual_state, sort_keys=True)}</visual_state>\n"
                 f"</page>\n\n{req.question}")
    messages = [*req.history, {"role": "user", "content": user_turn}]

    def sse():
        with client.beta.messages.stream(
            model="claude-opus-5-5",
            max_tokens=4000,
            system=system_blocks(req.module),   # last block carries cache_control
            messages=messages,
            output_config={"effort": "medium"},
            betas=["server-side-fallback-2026-07-01"],
            fallbacks="default",
        ) as stream:
            for text in stream.text_stream:
                yield f"data: {json.dumps({'delta': text})}\n\n"

    return StreamingResponse(sse(), media_type="text/event-stream")

Gradient-descent coach (structured output)

class Diagnosis(BaseModel):
    regime: Literal["converging", "oscillating", "diverging", "plateau", "saddle_stall"]
    evidence: str                 # cites only numbers from the facts
    theory_link_latex: str        # e.g. "\\eta\\lambda_{\\max} = 2.1 > 2"
    suggested_experiment: str
    socratic_question: str

@app.post("/api/gd-coach", response_model=Diagnosis)
def gd_coach(facts: TrajectoryFacts) -> Diagnosis:
    response = client.messages.parse(
        model="claude-opus-5-5",
        max_tokens=2000,
        system=COACH_SYSTEM,
        messages=[{"role": "user", "content": facts.model_dump_json()}],
        output_format=Diagnosis,
    )
    return response.parsed_output

Evaluating the AI

  • Tutor eval set: about 50 items per module from real pilot submissions plus items seeded from the misconception taxonomy, graded on math correctness, correct diagnosis, teaching quality, and no answer leakage.
  • Regression gate: the eval runs in CI on every prompt or knowledge-pack change and blocks merges that lower correctness.
  • Narration faithfulness: every number in a narration must appear in the fact sheet. Target 100%.
  • Human review: the teaching team audits a weekly sample of consented transcripts.
